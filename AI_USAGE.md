## Pivotal Developer Decision & Correction (Direct Example)

### Context: The Insecure Direct Object Reference (IDOR) & Authorization Bypass

The challenge specifically mandates:
> *"However, your backend should be designed so that one seller cannot modify another seller's data."*

### 1. What the AI Initially Suggested:
Early in the architectural design, the AI suggested a common REST pattern:
```
PUT /api/v1/sellers/{sellerId}/listings/{listingId}
PATCH /api/v1/sellers/{sellerId}/listings/{listingId}/status
```
In this initial proposal, the controller and service directly used the `{sellerId}` path variable from the URL to fetch and update the listing:
```java
// Naive approach initially generated by AI:
listingService.updateListing(pathSellerId, listingId, request);
```
While the AI added an authorization header placeholder, the business logic still trusted the path variable or client-supplied identifier.

### 2. Why I Flagged and Rejected It:
During code review, I recognized a critical security flaw: **Insecure Direct Object Reference (IDOR) / Authorization Bypass**.
If Seller 3 logged in and called:
```http
PUT /api/v1/sellers/7/listings/12
```
A naive path-variable check would either allow Seller 3 to modify Seller 7's price and stock, or fail to cryptographically prove that the authenticated caller actually owns Seller ID 7. Simply trusting the path variable created a porous authorization boundary.

### 3. How We Corrected It (The Session-Token Wristband Architecture):
I rejected trusting path variables and designed a dedicated server-side session wristband mechanism:

1. **Cryptographic Session Token Generation:**
   On login (`/api/v1/auth/login`) or registration, the backend issues an unforgeable, opaque session token (`UUID.randomUUID().toString()`) stored in the database.

2. **`SessionAuthFilter` (`OncePerRequestFilter`):**
   Intercepts incoming requests to `/api/v1/sellers/**`, reads the `X-Session-Token` header, performs a database lookup (`findBySessionToken`), and binds the real, authenticated `Seller` entity to `CurrentSellerContext` (`ThreadLocal`).

3. **Strict Ownership & URL Tamper Verification:**
   In `SellerListingController`, we added a verification guard before any handler executes:
   ```java
   private Seller getVerifiedSeller(Long pathSellerId) {
       Seller caller = CurrentSellerContext.get();
       if (caller == null) {
           throw new SecurityException("Authentication required: Missing or invalid session wristband.");
       }
       if (!caller.getId().equals(pathSellerId)) {
           throw new SecurityException("Access denied: You are authenticated as '" + caller.getName() + 
                   "' (Seller ID: " + caller.getId() + ") and cannot modify listings for Seller ID: " + pathSellerId);
       }
       return caller;
   }
   ```

4. **Guaranteed Scoping in the Service Layer:**
   When creating, updating, or deactivating listings, the service methods exclusively use the **verified caller's ID** retrieved from the server context:
   ```java
   listingRepo.findByIdAndSellerId(listingId, verifiedCallerId)
              .orElseThrow(() -> new SecurityException("Access denied: Listing does not belong to you."));
   ```

### Outcome
This architectural correction guaranteed that:
- It is impossible for any logged-in vendor to manipulate URL parameters to overwrite another competitor's price, stock, or active status.
- Testing the boundary is completely reproducible by changing the `X-Session-Token` header.
- Authentication remained lightweight without needing heavy OAuth2 / full Spring Security session infrastructure while delivering rock-solid isolation.

## Other Technical Decisions & Refinements
1. **Password Hashing with BCrypt:**
   Replaced initial plaintext prototype password comparisons with `spring-security-crypto`'s `BCryptPasswordEncoder`, including backwards-compatible migration for pre-seeded demo records.
2. **Optimistic Locking (`@Version`):**
   Explicitly required an entity `version` field in `SellerListing` and `UpdateListingRequest` so that simultaneous inventory updates trigger `ObjectOptimisticLockingFailureException` (returning HTTP 409 Conflict), rather than silent last-write-wins data loss.
3. **Database-Level Seller Status Isolation:**
   Enforced seller approval filtering at the repository query level (`JOIN FETCH ... WHERE l.seller.status = 'APPROVED'`) rather than in-memory filtering, preventing data leakage and ensuring scalability when catalogue size grows.
